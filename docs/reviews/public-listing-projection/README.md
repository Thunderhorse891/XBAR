# Public listing raw-response projection

Prepared candidate only. Production SQL requires separate owner approval. This reconstructs an unpublished candidate whose local workspace was lost; earlier local validation is not reused as proof for this candidate.

The current legacy resolver in `20261001090000_workspace_keyed_storage_expand.sql` subtracts six horse fields and otherwise returns the full horse payload, plus arbitrary listing payload fields and nested document entities. `publicShare.ts` filters only after these values have crossed the network. A caller with an authorized public or token-protected listing can therefore receive internal cost basis, insurance, location, activity and future unknown fields. No customer record was queried.

The prepared SQL replaces only the existing legacy function body. The public wrapper, selected-row Live/release/token checks, function signature, owner and ACL stay intact. Horse identity, sale price/status, existing buyer-readiness summary, public bloodline, approved real-photo metadata, existing certificate facts and canonical listing workspace identity use explicit scalar projections. Unknown nested fields and malformed objects do not cross the boundary. Buyer media signing still receives the canonical workspace and approved storage path. Original documents and gallery files are untouched.

The isolated PostgreSQL17.6 workflow from PR338 applies the repository schema to disposable synthetic auth/storage fixtures, restores the historical resolver, demonstrates the raw-response exposure as the anonymous role, applies this candidate, repeats the same valid buyer controls and privacy assertions, and repeats application for idempotence. It covers private/public access, wrong/missing tokens, missing release, archived/newer draft rows, malformed containers and storage-only approved media. Static Node contract tests separately pin unchanged authorization conditions and fixture isolation; they are not runtime SQL proof.

The SQL is retained under `supabase/checks/public-listing-projection.candidate.sql` rather than as an executable migration. The Supabase CLI could not initialize its read-only home configuration here; no production migration was generated or run. After independent review and synthetic SQL proof, an authorized operator can generate the formal migration, review the exact diff and apply it to staging first. Production application still needs explicit approval. Reverting to the historical body restores the disclosure and is not a safe privacy rollback.
