# Dedicated Stripe account: preparation only

This draft adds a pure, unconnected policy and fixtures. It does not change an endpoint, start a Stripe session, register a webhook, read credentials, or provision an account or database. Setting the proposed server-only `XBAR_DEDICATED_CHECKOUT_ENABLED` switch has no effect in this draft. Leave current production billing settings and existing subscriptions alone.

## Before wiring any live path

1. **Identify the legacy account.** Confirm the production key's account without exposing credentials. Reconcile app-linked customers, subscriptions, unsettled invoices and open sessions against the original account. Keep the original webhook, price mappings, payment settings, portal, and existing billing operational. A local entitlement, empty row, or missing Stripe object isn't proof that billing is absent. Stripe's [cross-account copy](https://docs.stripe.com/get-started/data-migrations/pan-copy-self-serve?copy-method=full) can retain the same Customer ID in both accounts, but does not copy subscriptions or invoices.
2. **Persist account ownership before a redirect.** Plan an additive, backwards-compatible schema change. Do not rewrite legacy rows. Resolve preexisting unscoped IDs only to a verified legacy account; otherwise refuse. Start dedicated checkout only for proven new, unlinked workspaces or explicitly dedicated bindings. Under the existing checkout claim, verify the scope and record the account/customer before exposing a session. Bind ownership to the account, customer and workspace in the database. Use isolated databases for sandbox rehearsals.
3. **Keep lifecycle actions account-aware.** Keep `/api/stripe/webhook` on its original secret and client; a second route needs a separate [endpoint signing secret](https://docs.stripe.com/webhooks#verify-events) and verified account/mode. Match on the account and customer, never metadata alone. Enforce ownership in the same transaction as `xbar_apply_subscription_event` writes, with account-scoped replay handling, so an old or retried event can't change the new binding. Route customer portal, failed-payment links and the account-deletion billing check to the bound account. Use authenticated XBAR links in failed-payment email, not short-lived Stripe portal sessions. Keep upgrade offers disabled until separately verified.
4. **Prove it in two Stripe sandboxes.** Exercise first purchase, duplicate click/open-session protection, renewal, failed payment and recovery, cancellation, refunds/disputes, both customer portals, and account-deletion refusals. Reject wrong signatures, scope mismatches, metadata-only events, and out-of-order delivery that would overwrite current state. Use verified test-mode prices and disposable data. Confirm tax obligations and registrations before enabling [Stripe Tax](https://docs.stripe.com/billing/taxes/collect-taxes).
5. **Stop new starts without stranding existing billing.** Only after gates, review, and release authorization should the server flag be used to enable dedicated checkout. If switched off later, do not offer fallback legacy checkout to dedicated customers. Already issued Checkout URLs may still complete, so retain both webhook and management paths. Preserve the deployment's rollback plan and data; do not delete or move existing Stripe objects as part of this cutover.

Account activation belongs to the owner. If authorized later, set distinct least-privilege Stripe keys and webhook signing secrets directly in the correct protected environment. Do not paste them in chat, code, or logs. Account IDs and Price IDs are not secrets, but avoid exposing them in public readiness responses. If legacy access or reconciliation remains unverified, the release stays on hold.
